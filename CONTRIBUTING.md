# Contributing to familiar-js

Thanks for your interest in contributing to `familiar-js`.

Contributions are welcome, including bug fixes, documentation improvements, new mascot states, accessibility improvements, examples, integrations, and feature enhancements.

## How to Contribute

1. Fork the repository.
2. Create a new branch for your change.
3. Make your changes.
4. Add or update tests where appropriate.
5. Ensure the project builds and existing tests pass.
6. Submit a pull request with a clear description of:
    - what changed
    - why it changed
    - any relevant implementation details

## Code Quality

Please keep contributions:

- focused and reasonably scoped
- consistent with the existing project structure and coding style
- backwards-compatible where possible
- documented when introducing new public APIs or configuration options
- accessible and responsive when affecting UI behavior

Avoid unrelated refactors in the same pull request unless they are necessary for the proposed change.

## Mascot and Asset Contributions

New mascot presets, visual states, and related assets are welcome.

When contributing visual assets:

- use appropriately optimized formats
- prefer WebP for raster assets used by the package
- preserve transparency where required
- keep naming and folder structure consistent with existing mascot presets
- include all required states where applicable
- only contribute assets that you own or have permission to redistribute

Do not submit copyrighted third-party characters, logos, artwork, or other material unless redistribution is explicitly permitted.

Contributors retain ownership of their own contributions. By submitting a
contribution, you agree that code contributions are distributed under the

## Forks and Derivative Projects

Forks are welcome.

If your fork or derivative project uses the mascot artwork or other CC BY 4.0
assets, that license requires you to preserve attribution and indicate that
changes were made, and it prohibits implying that the original creator
endorses your use (see `LICENSE-ASSETS.md`).

Beyond that legal requirement, as project etiquette (not a license
obligation) we ask that forks or derivative projects:

- identify themselves as a fork or derivative of `familiar-js`
- avoid implying the fork is the official `familiar-js` project
- avoid using the original author's name to endorse the fork without permission

You are encouraged to describe substantial changes you have made so users can clearly distinguish the derivative project from the original.

## Pull Requests

Before submitting a pull request:

- check for existing issues or pull requests covering the same change
- keep the pull request focused
- explain breaking changes clearly
- update documentation where necessary
- include screenshots or recordings for meaningful UI changes

Maintainers may request revisions before merging.

## Issues

When opening an issue, please include:

- a clear description of the problem or proposal
- reproduction steps where applicable
- expected behavior
- actual behavior
- browser/runtime/framework information if relevant
- screenshots or code samples when useful

## Security

Please do not publicly disclose security vulnerabilities in normal issues.

If a private security contact method is provided in the repository, use that instead.
